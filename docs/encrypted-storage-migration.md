# Encrypted storage modules and migration

`modules/system/fs` configures supported filesystem layouts. The encrypted EFI
layout has persistent encrypted root/swap and a separate encrypted key source;
its readiness dependency is generated by `cryptkey-readiness.nix`. Keeping
persistent swap available before mounting root is necessary for hibernation.

The declarative Disko layouts model provisioning and inventory. **Evaluating a
layout is not permission to format an existing disk.** Adopt Disko only after a
separately reviewed migration; retain real device identities and compare the
resulting unlock, mount and resume configuration before activation.

A real-disk migration requires an off-device encrypted backup with a tested
restore, off-device LUKS headers/recovery credentials, working rescue media and
a bootable fallback. Add and test new credentials before removing old ones.
Retain the old encrypted key source until new cold boot and resume are verified.
Do not reformat partitions, recreate swap or remove keyslots as a boot repair.
Destructive changes to a real disk require explicit permission.

Native checks `encrypted-boot`, `storage-password-boot`,
`storage-key-filesystem-boot`, `storage-disko-inventory` and
`storage-disko-provision` exercise actual systemd initrd unlock, candidate
credentials, configuration equivalence and provisioning on disposable VM disks.
Passing fixtures do not establish that a physical machine has a recoverable
backup or authorize applying their provisioning commands to it.
